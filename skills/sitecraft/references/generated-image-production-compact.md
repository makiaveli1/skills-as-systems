# Generated image production — compact

Use when custom imagery shapes a website.

1. Map each asset: stable asset ID, surface, purpose, semantic role, focal point, copy relationship, variants, loading, alt text, rights, owner, evidence.
2. Bound every reference as identity, composition, form, palette/material, lighting, environment, motion, exclusion, or other; state its exact contribution and what to ignore.
3. Declare image intent before execution: **generate** when references only guide a new image; **edit** when an existing image must remain while named parts change.
4. Plan distinct assets as distinct production jobs. Record dependencies, required approved inputs, edit sources, reference IDs and acceptance gates. Only independent jobs may run in parallel; dependent jobs wait for their declared gates.
5. For derivative families, restart each sibling from its declared approved parent unless the Experience Contract explicitly defines another lineage. Do not chain siblings accidentally.
6. Work still-first: brief → reference map → candidate stills → approved master → surgical repairs → responsive derivatives → separate motion handoff → rendered evidence.
7. Prompt in blocks: use, subject, reference roles, composition/crop safety, treatment, preserve, exclude, output. Repair one diagnosed defect at a time and repeat invariants on every edit.
8. Re-discover host capability before execution. A local path alone is not proof the image generator can see the reference. Confirm generation/edit access, reference loading, returned-image inspection and project import/persistence.
9. Gate **execution-context isolation** separately from prompt quality. For consequential/reference-dependent work, prefer an isolated request or fresh bounded image-only context. If paid API execution is unavailable, a fresh image-only subscription chat is a first-class route; on ChatGPT, prefer Temporary Chat outside the website Project, attach only the exact packet + declared reference image(s), and return the candidate for project persistence/review. If the generator may infer from unrelated conversation/project context, block that route. Unexpected workflow/UI/text leakage into the output is context contamination: reject it and change route rather than lengthening the prompt.
10. Choose by capability, not hype or price. Record tool/route, settings when known, limits, fallback, rights and lineage. Keep Sitecraft provider-neutral and do not require API spend when a bounded subscription chat, host-native included-quota image worker, local model, or human route satisfies the same contract.
11. Persist accepted project-bound assets into the workspace with stable semantic names; do not leave finals only in a chat, temporary URL, host generation folder or opaque tool history.
12. Without an image tool, return the portable [Image Generation Pack](../assets/image-generation-pack.md): production graph, ready prompts/edit instructions, reference table, preserve/reject lists, master/derivative specs, host preflight, focal guidance, checks and motion handoff.
13. Verify full resolution, real website composition, responsive crops, 320 CSS px, legibility, LCP/CLS, metadata, rights, reduced motion where relevant and owner approval.
